# Порядок проверки решения

## 1. Комплект и запуск

- Открыть [README](../README.md) и [презентацию](presentation.pdf).
- Проверить наличие исходников, `Dockerfile`, `compose.yaml`, `.dockerignore`, `requirements.txt`, `.env.example` и тестов.
- Запустить `docker compose up --build`, открыть `http://127.0.0.1:8000`.
- Проверить `/api/health`: база загружена, состояние API соответствует фактическим настройкам.
- Без ключа ожидать поиск и выдержки. Для модельного режима заполнить `.env` и повторить запуск.

## 2. Основной сценарий

Вопрос:

> Какая арендная плата по договору с ООО «Северный Склад» и до какого числа её нужно вносить?

Проверить, что выбран нужный договор, источник содержит 450 000 рублей с НДС и оплату до 5-го числа. Открыть цитату и сопоставить выделенный текст с утверждением. В офлайн-режиме это проверка выдержек; в модельном — ещё и сформированного ответа.

## 3. Уточнение и продолжение

В новом диалоге:

> Нужно ли одобрение до 12 млн рублей?

После уточнения даты ответить:

> 2024

Проверить, что ассистент сохранил первоначальный вопрос и рассматривает редакцию, применимую к 2024 году. В ответе с LLM проверить порог свыше 10 млн и необходимость одобрения до подписания по соответствующему регламенту. Смена темы должна прекратить перенос прежнего договора.

## 4. Отсутствующие данные

> Гарантия по П-99/2025?

Ассистент должен сообщить об отсутствии нужного источника, а не подставить условия похожего договора. Такой ответ может не иметь цитат: выдуманная ссылка не нужна для сообщения об отсутствии документа.

> Какой размер пособия по беременности и родам?

При отсутствии необходимых сведений в базе не должен появляться размер пособия из общих знаний модели.

## 5. История и источники

- Создать два диалога и переключиться между ними.
- Перезагрузить страницу: сообщения и незавершённое уточнение сохраняются.
- Открыть цитату: выделенный текст совпадает с источником.
- Удалить диалог и убедиться, что он не восстанавливается после обновления.
- Учитывать, что история относится к конкретному адресу, порту, профилю браузера и устройству; это не серверная синхронизация.

## 6. Модель и диагностика

При настроенном прокси проверить фактический режим ответа и статус самопроверки. В трассировке различать:

- настроен ли API и был ли реальный вызов генерации;
- получен ли пригодный текст;
- использовался ли dense-поиск, прошёл ли проверку готовый индекс;
- был ли применён реранкер или сработал возврат к исходному поиску;
- завершена ли самопроверка или сохранён черновик после её сбоя.

Не приравнивать `enabled` к успешному выполнению стадии. Не считать наличие источника достаточным доказательством правильности юридического вывода.

## 7. Автоматические проверки и CSV

```sh
python3 -m unittest discover -s tests -v
node tests/test_history_v11.js
python3 scripts/smoke.py
python3 solution.py --data-dir data --questions data/demo_questions.csv --output submission.csv --trace run_trace.jsonl
```

Проверить заголовки `id,answer`, сохранение входных ID, отсутствие пустых строк и переносов истории между независимыми вопросами. Файл `data/demo_questions.csv` — публичные примеры, а не независимый тест качества.

## 8. Финальная передача

- Для автоматического судьи использовать только `artifacts/submission-v20.zip`.
- Для финальной сдачи подготовить полный репозиторий или ZIP с исходниками, документацией и PDF-презентацией.
- На первом слайде PDF указать порядок проверки и ссылку на репозиторий; публичный интерфейс указывать только при наличии доступного жюри развёртывания.
- Если репозиторий приватный, предоставить доступ аккаунту `hack-and-change-2026`.
- Убедиться, что `.env`, токены, пользовательская история и рабочие журналы с чувствительными данными не включены в сдачу.
- До сдачи завершить фактическую проверку Docker на машине с Docker Engine и отдельно проверить целевой API. Текущий статус измерений приведён в [evaluation.md](evaluation.md).
