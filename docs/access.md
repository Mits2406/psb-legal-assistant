# Доступ к документам в веб-версии V21

V21 добавляет учётные записи и серверный отбор документов к прежнему ядру ответа. Архив `artifacts/submission-v20.zip` для автоматического судьи сохранён без изменений: в CSV нет пользователей и уровней доступа.

## Первый вход

При первом запуске создаются `user` с уровнем 1 и `admin` с уровнем 2. Общего пароля по умолчанию нет: для каждой установки генерируются отдельные пароли. При прямом запуске они записываются в `state/initial-credentials.txt` рядом с приватной базой `state/access.sqlite`.

При запуске через Compose состояние находится в именованном volume, подключённом к `/app/state`. Прочитать начальные пароли можно локально:

```sh
docker compose exec web cat /app/state/initial-credentials.txt
```

После запуска откройте `http://127.0.0.1:8000` и введите имя и пароль. Адрес конкретной локальной демоверсии может отличаться; текущая демоверсия запускается на `http://127.0.0.1:8014`. Эти адреса доступны только на компьютере, где работает сервер.

До первого запуска вместо генерации можно задать `PSB_USER_PASSWORD` и `PSB_ADMIN_PASSWORD` в приватном `.env`. Допустимы пароли длиной 8–1024 символа; браузерная форма принимает до 512 символов. Переменные применяются только при создании пользователей в пустой базе. Изменение `.env` и перезапуск не сбрасывают уже существующие пароли. Интерфейса смены паролей и создания дополнительных пользователей пока нет.

`PSB_STATE_DIR` задаёт каталог состояния. При прямом запуске значение по умолчанию — `state/` у приложения, в Compose — `/app/state`. SQLite-файл и файл начальных паролей создаются с правами `0600`. Не публикуйте каталог состояния, начальные пароли, `.env` или резервные копии этой базы. Ключи модельного API не передаются браузеру; учётные записи и рабочие секреты не входят в архив автоматического судьи.

## Что означают уровни

| Пометка документа | Уровень 1 | Уровень 2 |
|---|---|---|
| Без пометки | Видит | Видит |
| 1 | Видит | Видит |
| 2 | Не видит | Видит |

Уровень пользователя определяется серверной записью. Переключателя, который позволял бы получить уровень 2, в интерфейсе нет.

Чтобы изменить пометку, войдите как `admin`, откройте документ в базе или из цитаты, выберите 1 или 2 и нажмите «Сохранить доступ». Пометка хранится в SQLite и сохраняется после перезапуска. Обычный пользователь видит только значок разрешённого уровня, без управления. Прямой запрос скрытого документа вернёт 404; попытка уровня 1 изменить доступ — 403.

## Как ограничения влияют на LLM

Сервер сначала строит корпус разрешённых пользователю документов, а затем выполняет восстановление условий, поиск и формирование ответа. Изолируются реестр документов, BM25F, набор фрагментов для векторного поиска, кэши, реранжирование и контекст генерации/самопроверки. Ограничение действует также в режиме выдержек без LLM. Текст вопроса, присланный самим пользователем, остаётся его вводом и не становится авторизованным источником.

Изменение пометки повышает глобальный номер редакции прав `acl_revision`. Запросы предыдущей редакции не продолжают использовать старый контекст, а перед выдачей ответа сервер повторно проверяет права. Если они изменились во время обработки, пользователь начинает новый диалог. Уже отправленный до изменения прав запрос провайдеру модели отозвать нельзя; ранее прочитанный или скопированный документ также не исчезает с устройства пользователя.

## История диалогов

Завершённые ответы и состояние уточнения хранятся на сервере отдельно для каждой учётной записи и редакции прав. После входа или перезагрузки браузер получает историю через защищённый `/api/history`; в памяти вкладки остаётся только отображаемая копия. Клиент не отправляет собственную историю для включения в контекст LLM. Совпадение `conversation_id` у двух пользователей не даёт доступ к чужому диалогу.

После изменения доступа прежняя история скрывается целиком для всех пользователей, включая администратора. Эти записи остаются в SQLite, но больше не загружаются в интерфейс или модель. Кнопка «Удалить всю историю» удаляет серверные диалоги этой учётной записи во всех редакциях. Кнопка × удаляет отдельный диалог.

В браузере история не сохраняется в `localStorage`; прежний общий ключ удаляется. При выходе и смене пользователя очищаются сообщения, источники, текст открытого документа и ожидающие ответы. Сессия проверяется при возвращении фокуса и каждые 15 секунд в видимой вкладке; каждый запрос API дополнительно проверяется сервером. Если вкладка была закрыта до завершения ответа, после возвращения доступны те ответы, которые сервер успел сохранить.

Сессия действует до 8 часов. Cookie имеет `HttpOnly` и `SameSite=Strict`, изменяющие запросы требуют CSRF-токен. Для развёртывания с HTTPS используйте `PSB_COOKIE_SECURE=1`. Текущий комплект предназначен для локального прототипа; управление пользователями, SSO, аудит действий и шифрование базы на диске отдельно не реализованы.

## Как проверить

Ручные сценарии приведены в [чек-листе](review-checklist.md#6-два-уровня-доступа). Автоматические тесты:

- [test_access_control.py](../tests/test_access_control.py): учётные записи, сессии, пометки, редакции и серверная история.
- [test_access_http.py](../tests/test_access_http.py): вход, CSRF, HTTP-доступ, изоляция пользователей и смена прав во время запроса.
- [test_scoped_access.py](../tests/test_scoped_access.py): область поиска и модельных вызовов.

```sh
python3 -m unittest discover -s tests -p 'test_access*.py' -v
python3 -m unittest discover -s tests -p 'test_scoped_access.py' -v
```

Результаты проверок фиксируются в [evaluation.md](evaluation.md). Тест с контролируемым API подтверждает состав отправленных источников, но не качество модели организаторов.
